## 四、架构决策记录（已拍板，勿擅自推翻）

### 决策 1：输入方案 = Input System Package (New) + InputAction
- **不修改 Project Settings**，**不恢复 `Input.GetMouseButtonDown(0)`**
- 复用工程已有的 `Assets/InputSystem_Actions.inputactions`，**不新建输入资产**
- 挖矿与建筑放置**共用 `Player/Attack`** 动作，用 `performed` 回调 → 按住不连击

### 决策 2：奖励发放路径（预制体安全）
```
MiningInput → DamageSystem.CalculatePlayerDamage()
           → Ore.TakeDamage(damage)  返回 bool 是否击碎
           → 若击碎，MiningInput 读取 Ore.Reward
           → PlayerCurrency.AddMoney(reward)
```
**`Ore` 不持有、也不查找 `PlayerCurrency`**。

### 决策 3：矿石死亡 = 直接 `Destroy(gameObject)`
不做重生系统，不创建 `OreManager` / `OreSpawner` / `RespawnTimer`。

### 决策 4（阶段 2）：颜色是「原料的变体」，不拆成多个 MaterialData
库存按 **(原料, 颜色)** 二元组分格存放。枚举**新增值一律追加到末尾**。

### 决策 5（阶段 2）：库存用 `List<MaterialStack>`，不用 `Dictionary`
Unity 不能序列化 `Dictionary`。数量归零时整格移除。

### 决策 6（阶段 2）：购买的原子性由调用顺序保证
`TrySpendMoney` 失败时不动数值；`AddMaterial` 放在扣钱成功之后。

### 决策 7（阶段 2）：UI 用 uGUI + 旧版 `UnityEngine.UI.Text`
**绝不引入 TextMeshPro**。`EventSystem` 必须挂 `InputSystemUIInputModule`。创建 UI 时选 `Text (Legacy)` / `Button`，不要选带 TMP 字样的项。

### 决策 8（阶段 2）：UI 拿不到写入口
`Shop` 只把 `Currency` / `Inventory` 以**只读属性**暴露给 UI。

### 决策 9（阶段 3）：坐标换算用数学平面求交，不用物理射线
`BuildingPlacement.TryGetGroundPoint()` 用 `new Plane(Vector3.up, (0, groundHeight, 0))` + `Camera.ScreenPointToRay` + `Plane.Raycast`。
**理由**：不会被矿石、已放置建筑、玩家挡住，也不依赖地面有没有挂 Collider。代价是假定地面是水平面（当前成立）。

### 决策 10（阶段 3）：重叠检测用 `Physics.CheckBox`，不用 `OverlapBox`
只需要一个「有没有」的布尔值，`CheckBox` 不分配数组、语义最直接。
检测盒以落点为中心、**从地面向上**延伸 `overlapBoxHeight`：`center = point + Vector3.up * (overlapBoxHeight * 0.5f)`。

### 决策 11（阶段 3）：屏蔽挖矿靠禁用 `MiningInput` 组件，不改它的代码
进入放置模式时 `miningInput.enabled = false`，退出时恢复。
**代价（重要，见第六节踩坑 1）**：`MiningInput.OnDisable()` 会顺带 `Disable()` 那个共享的 `Player/Attack` 动作，而 `InputAction.Enable/Disable` **不是引用计数**的——所以 `BuildingPlacement` 必须自己把动作补回来。

### 决策 12（阶段 3）：恢复挖矿延到 `LateUpdate`，不在回调里当场恢复
`PlaceBuilding` 是从 `Player/Attack` 的 `performed` 回调里被调用的。当场重新启用 `MiningInput` 会让它在同一次回调派发过程中重新订阅该动作。延到帧末可让「确认放置的那一次点击」在时序上不可能同时触发挖矿。

### 决策 13（阶段 3）：蓝图自带防自检
`BuildingBlueprint.EnsureCached()` 会**禁用其所有子物体的 Collider**，避免蓝图被自己的 `Physics.CheckBox` 检测到。

### 决策 14（阶段 3）：建造模式的「进入/退出」与「有没有蓝图」解耦
- `BuildingCameraDirector` 自己维护 `inBuildMode` 状态
- **进入**：轮询 `buildingManager.IsPlacing`，一出现蓝图就自动进入
- **退出**：**只能**由玩家显式调用 `ExitBuildMode()`；放置成功**不**退出
- `ExitBuildMode()` 会顺手 `CancelSelection()`——否则下一帧「有蓝图就自动进入」会把相机立刻推回去，画面来回弹

### 决策 15（阶段 3）：UI 接线用「下标 + 数组」绕开 UnityEvent 的参数限制
Unity 的 `Button.OnClick` 只能传 `int/float/string/bool/Object`。`BuildingUI.SelectBuilding(int)` 用下标索引 `availableBuildings`，于是按钮只传一个整数。
**新增建筑时只需往 `availableBuildings` 数组里加一项**，不用改代码、不用重新接线。

### 决策 16（阶段 3）：配置走编辑器脚本，不直接改 `.unity`
见第六节踩坑 2。`BuildingSetupWizard` 在活动场景里建物体、接线，由 Unity 自己写文件。

| `BuildingManager` | 记住选中项、生成/销毁蓝图、生成实体建筑、维护已放置列表 | **不做坐标换算与重叠检测**、**不消耗材料**（阶段 4 才做） |

## 六、踩坑记录（**都是实际发生过的，不是理论风险**）

### 踩坑 1：`InputAction.Enable()/Disable()` 不是引用计数的 —— 曾经导致「蓝图能跟手但点不下去」

**源码实证**：`Library/PackageCache/com.unity.inputsystem@57d0e36f6123/InputSystem/Actions/InputAction.cs:907`

```csharp
public void Enable()
{
    using (k_InputActionEnableProfilerMarker.Auto())
    {
        if (enabled)
            return;          // ← 已经启用就直接返回，不是引用计数
```

**失败链条**（阶段 3 初版代码的真实 bug，已修）：

```
1. MiningInput.OnEnable()        → action.Enable()   动作启用
2. BuildingPlacement.OnEnable()  → action.Enable()   已是启用 → 空操作
3. 点建筑按钮 → BuildingManager.SelectBuilding()
   → SetMiningSuppressed(true) → miningInput.enabled = false
4. → MiningInput.OnDisable()     → action.Disable()  ← 动作被整个关掉
5. BuildingPlacement 订阅的是已禁用的动作 → OnConfirmPerformed 永不触发
```

**症状**：蓝图正常出现、正常跟随鼠标（`Update()` 不依赖输入动作），但点击地面毫无反应。

**修法**：`BuildingPlacement` 新增 `LateUpdate` → `EnsureConfirmActionEnabled()`，放置期间发现动作被关掉就补一次 `Enable()`；同时**删掉** `BuildingPlacement.OnDisable` 里的 `Disable()`（它会把 `MiningInput` 一起关掉，是同一个 bug 的镜像）。
放在 `LateUpdate` 是因为 `MiningInput.OnDisable` 是在 `SelectBuilding` 调用栈里同步触发的，那时仍在 `Update` 阶段。

> **成因是 Claude 的判断错误**：Claude 曾把「Input System 的 Enable/Disable 是引用计数的」当作事实写进代码注释，但从未验证过。

### 踩坑 2：Unity 开着场景时直接改 `.unity` 文件会造成编辑器内未保存改动丢失

Claude 曾直接编辑 `SampleScene.unity` 来加建筑系统物体。Unity 检测到外部改动后会整场重载，**编辑器里尚未保存的改动（用户当时手工做的按钮）一并消失**。

**规**：**今后一律不直接编辑 `.unity` / `.prefab`**。需要程序化配置时，写编辑器脚本由 Unity 自己执行（见规则 13）。纯资产的 `.asset`（ScriptableObject）风险较低，但同样应优先用编辑器脚本或让用户在 Inspector 里改。

### 踩坑 3：`MaterialPropertyBlock` / 材质透明度
URP 的 Lit 材质**只改颜色不改 Surface Type 是不会半透明的**。必须同时满足：`_Surface: 1`、`_SrcBlend: 5`、`_DstBlend: 10`、`_ZWrite: 0`、`m_ValidKeywords: [_SURFACE_TYPE_TRANSPARENT]`、`RenderType: Transparent`、`m_CustomRenderQueue: 3000`。本次两个蓝图材质的数值是照 URP 包自带的 `Sphere_Transparent.mat` 模板改的，不是凭记忆写的。

### 踩坑 4：手写 Unity YAML 时中文字符串
Unity 写非 ASCII 时会转义成 `\uXXXX`（双引号标量内）。但 **Unity 的读取端同时接受字面 UTF-8**。用工具写文件时注意 `\u` 可能被二次解释，`perl -pe 's/.../\\u84DD.../'` 会把它当成「下一个字母转大写」而产出错误结果。

**3. `ShopPanel` 在 1080 高度下顶部溢出**

验收专用。**验收通过后改回 `0`**，否则每次开局白送 10 金币。

**5. 建造机位是推算值**

`BuildingCameraDirector.buildingModePosition = (10.21735, 49.15, -43.9)`、`eulerAngles = (55, 0, 0)`。
这是按「地图中心 + 俯角 55° + 距离 60」反推出来的，**不是实测的**。俯角 55° 有个附带好处：竖直 FOV 60° 下屏幕最上沿也在水平线以下 25°，所以**整个屏幕的射线都会打到地面**，规避了常规机位只在屏幕下半部分能求交的问题。
**正确的定法**：在 Scene 视图里摆好镜头 → 右键 `BuildingCameraDirector` 组件 → `把相机当前位置记录为建筑模式机位`。

文件名是「砖块」，内部数据是「小砖」。阶段 3 的 `requiredMaterials` 引用的是这个资产，所以 `GetRequirementText()` 会打印 `小砖 ×3`。
**待用户确认这是有意命名还是需要统一。**

**7. 常规机位本身可能是未完成状态**

Main Camera 在 `(-20.93, 0.82, -12.9)`、rotation 全零——一个水平视角。这意味着**不在建造模式时**，`BuildingPlacement` 的地面求交只在屏幕下半部分能成功。建造模式内部不受影响（见第 5 条）。
若将来挖矿或其他玩法需要「点地面」，这个初始机位要重新摆。

### 设计歧义（尚未拍板，动相关代码前先问用户）

**8.（阶段 4 前置，重要）建筑用料是否指定颜色？**

`MaterialInventory` 按 **(原料, 颜色)** 二元组分格存放，而 `BuildingMaterialRequirement` **刻意不含颜色字段**。
所以「砖块 ×3」到底是「任意颜色合计 3 个」还是「指定颜色 3 个」，**必须由用户拍板**。阶段 3 只记录不消费，所以现在不影响任何东西。

**阶段 2/3 的处理：只存不算。**

**10. 挂机/自动产出无归属**
建议并入 `BuildingEffect`（自带 tick），不新增顶层模块。

**11. 建筑移除的玩家入口**
`BuildingManager.RemoveBuilding(GameObject)` 已实现，但**没有任何 UI 调用它**。阶段 3 未做拆建筑按钮，也未做材料退回（那是阶段 4）。

**12. 将来做存档时会缺稳定 ID**
`MaterialData` 与 `BuildingData` 都只有显示名。跨会话存档用名字当键是脆的，建议后续加 `materialId` / `buildingId`。

**13. 提示文案**
阶段 2 的提示行是 `ShopUI` 内部的。建筑系统的状态提示（「不能放在这里」「原料不足」）出现时，建议抽成共用 `ToastUI`。

## 九、必须遵守的项目规则（用户明确定下）

1. **严格分阶段**。已完成阶段不要自动开始下一阶段，**等用户指令**。
2. **不要擅自修改策划案**。先指出「问题 / 原因 / 推荐方案 / 对后续系统的影响」，再在不影响 MVP 的前提下选最简单的实现。
3. **数值不硬编码**。矿石 HP、奖励、攻击力、伤害倍率、原料价格、建筑占地、相机机位等必须能在 Inspector 或 ScriptableObject 中调整。
4. **禁止** `FindObjectOfType` / `GameObject.Find` 作为主要架构手段，优先 `[SerializeField]` 引用。
5. **禁止静默失败**。用 `Debug.LogWarning` / `Debug.LogError` 给出明确提示。
6. **避免循环依赖**，避免一个 Manager 包办所有系统，不为简单功能引入复杂设计模式。
7. **不要扩大范围**。不要因为架构调整而重写已完成的脚本，除非确实有编译错误。如必须改，先列出「文件 / 修改原因 / 对已有功能的影响」，再给完整代码。
8. **所有 `.cs` 文件给完整代码**，不要只给片段。
9. 回答时**不要过分夸赞**；承认自己可能出错；标明哪些是实证、哪些是推断；必要时主动索要补充信息或证据。
10. **不引入 TextMeshPro**。UI 文字用旧版 `UnityEngine.UI.Text`。
11. **场景配置问题直接解析 YAML**。`SampleScene.unity`、`*.asset` 都是 YAML，读它们比问用户更快更准。
    **但反过来不成立**——见规则 13。
12. **类名与命名空间同名是坑**。`Yujian.Shop` 命名空间里有类 `Shop`，在其他 `Yujian.*` 命名空间里直接写 `Shop` 会被解析成命名空间并报 **CS0118**。
    `ShopUI.cs` 里用的是全限定名 `Yujian.Shop.Shop`，**带注释说明，不是笔误，请勿「简化」**。
    **阶段 3 已遇到同类风险的规避**：建筑相机脚本命名 `BuildingCameraDirector` 而不是放在 `Yujian.Camera` 命名空间（会与 `UnityEngine.Camera` 冲突）。
13. **不要直接编辑 `.unity` / `.prefab` 文件**（阶段 3 新增，见第六节踩坑 2）。
    需要程序化配置时写**编辑器脚本**（放在 `Editor/` 文件夹），由用户在菜单里执行，让 Unity 自己写文件。
    例外：`.asset`（ScriptableObject）风险较低，但仍优先用编辑器脚本或让用户在 Inspector 里改。
