| 项目 | 内容 |
|---|---|
| 游戏 | 《屿见》——鼓浪屿建设主题、竖屏 3D Lowpoly 俯视视角、休闲/增量 |
| 工程路径 | `D:\Unity stuff\屿见` |
| 引擎 | Unity 6000.3.8f1 |
| 渲染管线 | URP 17.3.0 |
| 输入系统 | Input System 1.18.0 |

**成因与修法见踩坑 5。** 两条路：① **重跑菜单 `屿见/建筑/配置建造系统（阶段 4）`**（向导已补上 `SetActive(true)`，会重建整个面板，最干净）；② 在 Inspector 里手工把那两个按钮名字左边的勾打上再 `Ctrl+S`（立刻见效，但根因在向导，不建议当长期做法）。

> 面板的 `Panel Root` **必须**指向 `Content` 子物体，不能指向挂 `BuildingMaterialPanel` 的那个物体本身 —— 否则 `SetActive(false)` 会把组件自己也停掉，面板再也回不来。`Awake()` 里有一条针对这个的错误提示。
> `SlidingPanel` 挂在**面板**上、`target = Content`，是同一个道理：滑完它停用的是 `Content`，它自己必须留在激活物体上才滑得回来。

## 四、架构决策记录（已拍板，勿擅自推翻）

### 决策 1：输入方案 = Input System Package (New) + InputAction
- **不修改 Project Settings**，**不恢复 `Input.GetMouseButtonDown(0)`**
- 复用工程已有的 `Assets/InputSystem_Actions.inputactions`，**不新建输入资产**
- 挖矿与建筑放置**共用 `Player/Attack`** 动作，用 `performed` 回调 → 按住不连击

### 决策 2：奖励发放路径（预制体安全）
```
MiningInput → DamageSystem.CalculatePlayerDamage()
           → Ore.TakeDamage(damage)  返回 bool 是否击碎
           → 若击碎，MiningInput 读取 Ore.Reward
           → PlayerCurrency.AddMoney(reward)
```
**`Ore` 不持有、也不查找 `PlayerCurrency`**。

### 决策 3：矿石死亡 = 直接 `Destroy(gameObject)`
不做重生系统，不创建 `OreManager` / `OreSpawner` / `RespawnTimer`。

### 决策 4（阶段 2）：颜色是「原料的变体」，不拆成多个 MaterialData
库存按 **(原料, 颜色)** 二元组分格存放。枚举**新增值一律追加到末尾**。

### 决策 5（阶段 2）：库存用 `List<MaterialStack>`，不用 `Dictionary`
Unity 不能序列化 `Dictionary`。数量归零时整格移除。

### 决策 6（阶段 2）：购买的原子性由调用顺序保证
`TrySpendMoney` 失败时不动数值；`AddMaterial` 放在扣钱成功之后。

### 决策 7（阶段 2）：UI 用 uGUI + 旧版 `UnityEngine.UI.Text`
**绝不引入 TextMeshPro**。`EventSystem` 必须挂 `InputSystemUIInputModule`。创建 UI 时选 `Text (Legacy)` / `Button`，不要选带 TMP 字样的项。

### 决策 8（阶段 2）：UI 拿不到写入口
`Shop` 只把 `Currency` / `Inventory` 以**只读属性**暴露给 UI。

### 决策 9（阶段 3）：坐标换算用数学平面求交，不用物理射线
`BuildingPlacement.TryGetGroundPoint()` 用 `new Plane(Vector3.up, (0, groundHeight, 0))` + `Camera.ScreenPointToRay` + `Plane.Raycast`。
**理由**：不会被矿石、已放置建筑、玩家挡住，也不依赖地面有没有挂 Collider。代价是假定地面是水平面（当前成立）。

### 决策 10（阶段 3）：重叠检测用 `Physics.CheckBox`，不用 `OverlapBox`
只需要一个「有没有」的布尔值，`CheckBox` 不分配数组、语义最直接。
检测盒以落点为中心、**从地面向上**延伸 `overlapBoxHeight`：`center = point + Vector3.up * (overlapBoxHeight * 0.5f)`。

### 决策 11（阶段 3）：屏蔽挖矿靠禁用 `MiningInput` 组件，不改它的代码
进入放置模式时 `miningInput.enabled = false`，退出时恢复。
**代价（重要，见第六节踩坑 1）**：`MiningInput.OnDisable()` 会顺带 `Disable()` 那个共享的 `Player/Attack` 动作，而 `InputAction.Enable/Disable` **不是引用计数**的——所以 `BuildingPlacement` 必须自己把动作补回来。

### 决策 12（阶段 3）：恢复挖矿延到 `LateUpdate`，不在回调里当场恢复
`PlaceBuilding` 是从 `Player/Attack` 的 `performed` 回调里被调用的。当场重新启用 `MiningInput` 会让它在同一次回调派发过程中重新订阅该动作。延到帧末可让「确认放置的那一次点击」在时序上不可能同时触发挖矿。

### 决策 13（阶段 3）：蓝图自带防自检
`BuildingBlueprint.EnsureCached()` 会**禁用其所有子物体的 Collider**，避免蓝图被自己的 `Physics.CheckBox` 检测到。

### 决策 14（阶段 3）：建造模式的「进入/退出」与「有没有蓝图」解耦
- `BuildingCameraDirector` 自己维护 `inBuildMode` 状态
- **进入**：轮询 `buildingManager.IsPlacing`，一出现蓝图就自动进入
- **退出**：**只能**由玩家显式调用 `ExitBuildMode()`；放置成功**不**退出
- `ExitBuildMode()` 会顺手 `CancelSelection()`——否则下一帧「有蓝图就自动进入」会把相机立刻推回去，画面来回弹

### 决策 15（阶段 3）：UI 接线用「下标 + 数组」绕开 UnityEvent 的参数限制
Unity 的 `Button.OnClick` 只能传 `int/float/string/bool/Object`。`BuildingUI.SelectBuilding(int)` 用下标索引 `availableBuildings`，于是按钮只传一个整数。
**新增建筑时只需往 `availableBuildings` 数组里加一项**，不用改代码、不用重新接线。

### 决策 16（阶段 3）：配置走编辑器脚本，不直接改 `.unity`
见第六节踩坑 2。`BuildingSetupWizard` 在活动场景里建物体、接线，由 Unity 自己写文件。

## 五、职责边界（不要越界）

| 类 | 允许 | 禁止 |
|---|---|---|
| `MiningInput` | 收输入、判 UI、射线检测、调 DamageSystem、调 TakeDamage、发奖励 | 不自己算伤害、不自己扣血 |
| `DamageSystem` | 只做 `基础攻击力 × 伤害倍率` | 不碰矿石血量/金币/UI/动画 |
| `Ore` | 自身血量、自身奖励数据、受击表现、死亡 | 不碰金币、不处理输入、不查玩家 |
| `PlayerCurrency` | 存钱、加钱、扣钱、广播变化 | 不知道矿石、原料、商店存在 |
| `MaterialData` | 描述原料是什么 | 不知道金币、库存、商店、玩家 |
| `MaterialInventory` | 按 (原料, 颜色) 存取、广播变化 | 不买、不卖、不算钱 |
| `Shop` | 校验 → 读价 → 扣钱 → 入库存 | 不持有 UI、不知道按钮长什么样 |
| `ShopUI` | 显示、把点击转交 `Shop.TryBuy` | **不得直接修改 money 或 inventory** |
| `BuildingData` | 描述建筑是什么 | 不知道玩家、不知道库存、**不含任何建造逻辑**，也不知道自己被谁选中了 |
| `BuildingBlueprint` | 显示自身、绿/红两态 | 不判定能不能放（那是 `BuildingPlacement` 的事）、不生成实体建筑 |
| `BuildingManager` | 记住选中项、生成/销毁蓝图、生成实体建筑、维护已放置列表 | **不做坐标换算与重叠检测**、**不消耗材料**（阶段 4 才做） |
| `BuildingPlacement` | 屏幕坐标→世界坐标、移动蓝图、检测重叠、提交放置 | 不自己生成建筑、不持有状态 |
| `BuildingCameraDirector` | 两个机位之间的过渡、维护 `inBuildMode` | 不做输入、不做放置判定 |
| `BuildingUI` | 把按钮点击转成对 `BuildingManager` / `BuildingCameraDirector` 的调用 | **不持有任何状态**，只做转发 |
| `GameManager` | 持有引用、启动自检 | **不是万能管理器** |

**依赖方向**：`BuildingUI` → `BuildingManager` / `BuildingCameraDirector`；`BuildingPlacement` → `BuildingManager`；`BuildingCameraDirector` → `BuildingManager`。**`BuildingManager` 不知道另外三者的存在**（只被读 `IsPlacing`）。

## 六、踩坑记录（**都是实际发生过的，不是理论风险**）

### 踩坑 1：`InputAction.Enable()/Disable()` 不是引用计数的 —— 曾经导致「蓝图能跟手但点不下去」

**源码实证**：`Library/PackageCache/com.unity.inputsystem@57d0e36f6123/InputSystem/Actions/InputAction.cs:907`

```csharp
public void Enable()
{
    using (k_InputActionEnableProfilerMarker.Auto())
    {
        if (enabled)
            return;          // ← 已经启用就直接返回，不是引用计数
```

**失败链条**（阶段 3 初版代码的真实 bug，已修）：

```
1. MiningInput.OnEnable()        → action.Enable()   动作启用
2. BuildingPlacement.OnEnable()  → action.Enable()   已是启用 → 空操作
3. 点建筑按钮 → BuildingManager.SelectBuilding()
   → SetMiningSuppressed(true) → miningInput.enabled = false
4. → MiningInput.OnDisable()     → action.Disable()  ← 动作被整个关掉
5. BuildingPlacement 订阅的是已禁用的动作 → OnConfirmPerformed 永不触发
```

**症状**：蓝图正常出现、正常跟随鼠标（`Update()` 不依赖输入动作），但点击地面毫无反应。

**修法**：`BuildingPlacement` 新增 `LateUpdate` → `EnsureConfirmActionEnabled()`，放置期间发现动作被关掉就补一次 `Enable()`；同时**删掉** `BuildingPlacement.OnDisable` 里的 `Disable()`（它会把 `MiningInput` 一起关掉，是同一个 bug 的镜像）。
放在 `LateUpdate` 是因为 `MiningInput.OnDisable` 是在 `SelectBuilding` 调用栈里同步触发的，那时仍在 `Update` 阶段。

> **成因是 Claude 的判断错误**：Claude 曾把「Input System 的 Enable/Disable 是引用计数的」当作事实写进代码注释，但从未验证过。

### 踩坑 2：Unity 开着场景时直接改 `.unity` 文件会造成编辑器内未保存改动丢失

Claude 曾直接编辑 `SampleScene.unity` 来加建筑系统物体。Unity 检测到外部改动后会整场重载，**编辑器里尚未保存的改动（用户当时手工做的按钮）一并消失**。

**规**：**今后一律不直接编辑 `.unity` / `.prefab`**。需要程序化配置时，写编辑器脚本由 Unity 自己执行（见规则 13）。纯资产的 `.asset`（ScriptableObject）风险较低，但同样应优先用编辑器脚本或让用户在 Inspector 里改。

### 踩坑 3：`MaterialPropertyBlock` / 材质透明度
URP 的 Lit 材质**只改颜色不改 Surface Type 是不会半透明的**。必须同时满足：`_Surface: 1`、`_SrcBlend: 5`、`_DstBlend: 10`、`_ZWrite: 0`、`m_ValidKeywords: [_SURFACE_TYPE_TRANSPARENT]`、`RenderType: Transparent`、`m_CustomRenderQueue: 3000`。本次两个蓝图材质的数值是照 URP 包自带的 `Sphere_Transparent.mat` 模板改的，不是凭记忆写的。

### 踩坑 4：手写 Unity YAML 时中文字符串
Unity 写非 ASCII 时会转义成 `\uXXXX`（双引号标量内）。但 **Unity 的读取端同时接受字面 UTF-8**。用工具写文件时注意 `\u` 可能被二次解释，`perl -pe 's/.../\\u84DD.../'` 会把它当成「下一个字母转大写」而产出错误结果。

### 踩坑 5：从「隐藏的按钮样品」克隆出来的 UI 是关闭的 —— 场景里有、屏幕上没有

`Object.Instantiate` 复制的是 **`activeSelf`**，**不是** `activeInHierarchy`。本工程里的按钮样品全是隐藏的：
`Canvas/ShopPanel/ButtonTemplate`（`SampleScene.unity:2295`，`m_IsActive: 0`）、两个 `ItemTemplate` 的根也一样，只当样板。
谁克隆了它们，**必须自己 `SetActive(true)`**。

**2026-10-07 的实际故障**（用户原话：「没有确认建造的按钮」「点了没有反应」）：
阶段 4 向导的 `CreateButton()` 只 `Instantiate`、没有激活，于是 `Button_确认建造` / `Button_撤回` **一出生就是关闭的**。
而同一批做出来的材料条目**看得见** —— 因为条目由 `BuildingMaterialPanel.CreateItem()` 在运行时 `SetActive(true)`，**只有这两个按钮没人替它们打开**。
症状就变成「条目都在，就是没有按钮」，点击当然也没反应（未激活的物体根本收不到射线）。

**为什么现在才出**：向导是用 `canvas.GetComponentsInChildren<Button>(true)` 现找样板的，只跳过直接父物体叫 `BuildingPanel` / `材料面板` 的。
阶段 2 重构之后，**商店的按钮全都搬进了那个隐藏的 `ItemTemplate` / `ButtonTemplate` 里**，于是被挑中当样板 —— 之前挑中的是可见的 `RedButton`，所以没暴露。

**两条规**：
1. 克隆 UI 样品后**显式激活克隆体**（`BuildingConstructionSetupWizard.CreateButton` 已补 `clone.SetActive(true)`，并写了注释）。
   `ItemTemplate` 那条路不受影响：条目是运行时逐个激活的。
2. `BuildingMaterialPanel.WireButtons()` 新增 `WarnIfInactive()`：引用在、连线也在、却仍然看不见时，当场报错点名。
   判的是 `activeSelf` 而**不是** `activeInHierarchy` —— 面板平时整个关着（`SlidingPanel` 会停用 `Content`），判后者会天天误报。

**2026-10-08 第二次出现（阶段 6 整合后第一次进 Play）**：
阶段 3 向导的 `BuildingSetupWizard.CreateButton()` **从来没有**补 `clone.SetActive(true)` ——
上面那条「已补」只做到了**阶段 4** 的 `BuildingConstructionSetupWizard.CreateButton`。
于是 `Canvas/BuildingPanel` 里那三个按钮（`Button_风琴博物馆` / `Button_取消蓝图` / `Button_退出建造`）
`m_IsActive` 全是 **0**，表现就是用户报的那句「建筑模块点开后没有蓝图选项」：
面板本身**确实**打开了（`m_IsActive: 1`），但它没有背景图，孩子又全关着，所以屏幕上是一片空白、Console 一句红字不给。
**只要重跑一次阶段 3 向导，就会重新造出三个关闭的按钮**（克隆体的 `activeSelf` 来自那个隐藏的 `ButtonTemplate`）。
2026-10-08 已补上源头那一行，并让阶段 6 向导负责修好**已经坏掉的场景** —— 详见 §15.14。

> **查场景时注意**：`m_IsActive: 0` 出现在 `Content` / 两个 `ItemTemplate` / `ButtonTemplate` 上是**预期**的（样板，或运行时才打开的内容根），**不要顺手「修好」**。
> 2026-10-07 排查时，整个场景只有 6 个未激活物体，其中 4 个是预期的，只有那 2 个按钮是真缺陷。

### 踩坑 6：克隆进「未激活的父物体」时 `Awake` 不会跑 —— 引用解析必须能重入

`Instantiate` 到一个**未激活**的父物体下，克隆体的 `activeSelf` 可能是 `true`，但整条激活链是断的：
**Unity 不会调用 `Awake`**，要等父物体被激活才补上。而调用方往往在 `Instantiate` 之后**立刻**调 `Initialize()`。

**2026-10-07 的实际故障**：材料条目在 `Content` 还关着的时候被克隆，`MaterialDragItem.Awake()` 没跑，
`background` / `label` 都是 `null`，于是颜色和数量全刷不上去，条目永远保持模板原样（白底 + 占位文字「Button」，见 `ButtonTemplate` 子物体 `Text (Legacy)` 的 `m_Text: Button`）。
用户看到的就是「一堆写着 Button 的方块，认不出是哪种料」。

**规**：把引用解析抽成幂等的 `ResolveReferences()`，`Awake()` 与 `Initialize()` **都调一次**（真正生效的是 `Initialize` 里那一次）。

`BuildingCameraDirector.buildingModePosition = (10.21735, 49.15, -43.9)`、`eulerAngles = (55, 0, 0)`。

**正确的定法**：在 Scene 视图里摆好镜头 → 右键 `BuildingCameraDirector` 组件 → `把相机当前位置记录为建筑模式机位`。

**6. `Material_砖块.asset` 的 `materialName` 是「小砖」**

文件名是「砖块」，内部数据是「小砖」。阶段 3 的 `requiredMaterials` 引用的是这个资产，所以 `GetRequirementText()` 会打印 `小砖 ×3`。
**待用户确认这是有意命名还是需要统一。**

**7. 常规机位本身可能是未完成状态**

Main Camera 在 `(-20.93, 0.82, -12.9)`、rotation 全零——一个水平视角。这意味着**不在建造模式时**，`BuildingPlacement` 的地面求交只在屏幕下半部分能成功。建造模式内部不受影响（见第 5 条）。
若将来挖矿或其他玩法需要「点地面」，这个初始机位要重新摆。

### 9.1 任务执行流程（2026-10-20 新增，用户明确定下）

### 11.3 架构决策（阶段 4 新增）

**决策 17：点地面 = 蓝图落位，不等于建造。**
`Placing`（跟鼠标）与 `Filling`（冻结等填料）两个相位，落位后 `BuildingPlacement` 完全让开。
**理由**：材料面板是屏幕 UI，从它上面按下拖动时鼠标必然在面板范围内；如果蓝图仍跟鼠标，它会跑到面板底下，拖拽目标根本不在屏幕上。
**这也是为地图方格留的接口**：将来「选格落位」与「建造」天然是两步。

**决策 18：落位坐标存在 `BuildingManager.anchoredPosition`，实体建筑生成在这个值上。**
不是「蓝图销毁前恰好所在的 transform」。将来方格系统只需要在**这一个值**上做吸附与占用登记。
`IsPlacementValid()` 保持是「这里能不能放」的唯一判定入口，方格模块替换它即可，不牵动别处。

**决策 19：材料的真相在 `BuildingConstruction.placementHistory`，它同时就是撤回栈。**
`List<PlacedMaterial>` 按放入顺序追加，撤回永远取末尾 —— 天然满足规格里的「后进先出」（A→B→C 撤回 C→B→A），不需要额外的双份历史。

**决策 20：材料在「拖进蓝图」的那一刻扣库存，确认建造时不再扣。**
否则撤回逻辑没有意义。`CanAcceptMaterial` 在**拖拽开始**时就跑一次，不合法则**不生成拖拽残影**，
直接给提示（规格第三条：「库存没有对应材料 → 不能生成拖拽物」）。

**决策 21：所有销毁蓝图的路径都走 `BuildingManager.CloseBlueprint(bool)`，由 `OnBlueprintClosed` 事件通知退料。**
取消蓝图 / 退出建造 / 切换建筑都走这条路，`built=false` → 材料全部退回库存。
**不退回就是凭空吞掉玩家的料**；规格只写了「撤回」怎么退，没写「取消」怎么办，这里按不吞料处理。
`built=true`（建成）时只清空历史，此后不能再通过蓝图系统撤回（规格第七条）。

**决策 22：层数由 `BuildingData.RequiredMaterials` 的总数决定，不写死。**
`BuildingLayerStack` 预制体里预置 3 层只是**样板**，运行时按需要的层数克隆到够用，并均分总高。
风琴博物馆 Brick×3 → 3 层，每层 4/3 高（总高仍是 4）；将来 Wood×5 → 5 层，每层 0.8。
自下而上第 i 层取第 i 块材料的颜色。

**决策 23：需求只认 `MaterialType`，颜色不参与匹配。**
「砖块 ×3」= 任意颜色的砖块合计 3 个（用户 2026-10-07 拍板）。
颜色**只影响最终建筑外观**。`BuildingMaterialRequirement` 仍然不含颜色字段，不用改。
这一条同时解掉了第七节未决事项 8。

**决策 24：面板条目由「需求的 MaterialData × 它的 AllowedColors」推导，数量为 0 的也列出来。**
只列「库存里有的」的话，玩家永远拖不到一个数量为 0 的条目，「原料不足，请购买」就永远触发不到。
0 数量的条目会压暗，但**保留 raycastTarget** —— 点下去要能收到提示，禁用条目就是静默失败。

**决策 25：蓝图的材料楼层必须排除在 `BuildingBlueprint` 的绿/红整体换材质之外。**
否则玩家放进去的红砖蓝砖会被绿/红盖掉，而「蓝图显示三块材料」正是阶段 4 的验收点。

**决策 26（本轮）：材料面板的显隐跟 `IsPlacing`，不跟 `IsFilling`。**
选中建筑那一刻面板就该出现，落位前后都能看到「这座建筑要什么料、还差几个」，不用先点一下地面才给看。
（`IsPlacing` = 从选中到蓝图关闭一直为真；`IsFilling` = 落位之后才为真。）

**决策 27（本轮）：面板贴屏幕底部居中，滑入 / 滑出用自写的 `SlidingPanel`，不引 Animator、不引补间库。**
`SlidingPanel` 挂在**面板**上，`target = Content`；「显示位」= 场景里摆好的 Y（+30），「隐藏位」= 显示位 + `hiddenOffsetY`（-610）。
用 `Time.unscaledDeltaTime`（面板显隐不该被 `Time.timeScale = 0` 冻住）+ `SmoothStep` 缓动；滑完把 `Content` 停用，省掉隐藏面板每帧的 UI 重建与射线检测。
**为什么是底部居中而不是右下角**：右下角被没有任何脚本控制的 `BuildingPanel` 常驻占着（x 1570~1890、y 30~290），而 `材料面板` 是 Canvas 最上层，盖上去会把它的按钮吞掉、点不到。底部居中（x 770~1150）同时避开左下角的商店面板（到 x=540 为止）和右下的建筑面板。

**决策 28（本轮）：`确认建造` 始终可点，材料不齐时由状态行说明差几个。**
`RefreshConfirmButton()` **刻意不再**把按钮设成 `interactable = false`：灰掉的按钮点下去连一句提示都没有，玩家只会觉得「按钮坏了」，
而 `BuildingConstruction.ConfirmBuild()` 里那句「材料还不够：小砖 0/3」也就永远跑不到（规则 5）。按钮的可点性完全交给 Inspector（规则 3）。
**这条同时取代了 11.7 / 11.8 里原来「凑齐前不可点」的写法。**

### 11.5 与 MaterialInventory / BuildingData 的连接方式

**与 `MaterialInventory`**（唯一真相源，`BuildingConstruction` 单向依赖它）：
- 放入：`inventory.RemoveMaterial(material, color, 1)`，成功才记账
- 撤回：`inventory.AddMaterial(material, color, 1)`
- 只读计数：`inventory.GetMaterialCount(material, color)`（面板显示用）
- 面板订阅 `inventory.OnInventoryChanged` 刷新数量

**与 `BuildingData`**（需求来自它，`BuildingConstruction` 不认识任何具体建筑）：
- `data.RequiredMaterials` → 每条 `BuildingMaterialRequirement.Material` + `.Amount`
- `.Material.AllowedColors` → 面板列哪些颜色
- `data.BuildingPrefab` → 建成什么
- **代码里没有任何 `Brick` / `×3` 之类的字面量**。加一个「原木 ×5 + 石头 ×2」的建筑，
  `BuildingConstruction` 与 `BuildingMaterialPanel` 一行都不用改，只要在 Inspector 里配需求。

- **攻击频率** `AttackInterval = 1`（策划案没给数值 → 走 Inspector，必须可调）。
- **攻击范围** `AttackRange = 5`（同上，MVP 默认值）。

  射程这个概念不再成立，字段已删除（见决策 34、第七节第 14 条）。
- **伤害 = 玩家当前的单次攻击伤害**：必须调 `DamageSystem.CalculatePlayerDamage()`，

- 表现：MVP 用 `Debug.DrawLine` 就够，不要做复杂特效。
- 必须用 `OnDrawGizmosSelected()` 显示攻击范围，方便策划调。
  ⚠️ **"范围"同样已失去含义**（决策 34）：Gizmo 仍在，但改成把**当前能打到的矿石逐个连线标出**，
  并给不在 Ore 层上的矿石画灰色空心块（图层配错时一眼可见）。见 `OrganMuseumAutoAttack.OnDrawGizmosSelected()`。
- **不要实现阶段 6。**

### 14.2 架构

```
Building（建筑预制体实例，由 BuildingManager.BuildAtAnchor 生成）
    └─ BuildingEffect（抽象基类，只管生命周期：初始化 / 停用）
          └─ OrganMuseumAutoAttack（风琴博物馆：自动攻击矿石）
                ├─ DamageSystem.CalculatePlayerDamage()   ← 伤害只有这一个来源
                ├─ FindObjectsByType<Ore>() + oreLayers 过滤 ← 找目标（无射程）
                └─ Ore.TakeDamage() + PlayerCurrency.AddMoney()

场景侧：GameManager（Instance） ──提供──> DamageSystem / PlayerCurrency
```

**谁不认识谁**（这是本阶段最要紧的一条）：

| 组件 | 知不知道"效果" | 说明 |
|---|---|---|
| `BuildingManager` / `BuildingData` / `BuildingConstruction` | **完全不知道** | 一行都没改。它们只负责把建筑实例生成出来 |
| `BuildingEffect` / `OrganMuseumAutoAttack` | 只知道自己 | 挂在预制体上，建成后自己初始化、自己计时、随物体销毁自动停 |
| `MiningInput`（玩家手动挖矿） | 不知道建筑 | 与建筑攻击**共用** `DamageSystem` 一套公式，所以两边伤害必然一致 |

### 14.3 新增决策

**决策 29：效果挂在建筑预制体上，场景服务从 `GameManager.Instance` 注入。**

- 备选方案是"阶段 4 的 `BuildingManager` 加一个 `OnBuildingBuilt` 事件 + 一个场景侧的 Host 组件，
  由 Host 把 `DamageSystem` 推给效果"。**没选**：那要动阶段 4 的代码，而收益只是"不用单例"。
- 为什么预制体必须走全局入口：`DamageSystem` / `PlayerCurrency` 住在**场景**里，预制体资产持有场景引用
  只会存成 Missing。`GameManager` 的类注释本来就写着"供没有场景引用可挂的系统（例如后续的 UI）访问"——
  **建筑效果就是它说的那种系统**。
- 代价：效果依赖场景里有 `GameManager`。缺了会**明确报错并拒绝启动**（不半启动），向导也会提前拦一道。

**决策 30：效果"自启动"——`BuildingEffect.Start()` 里兜底调 `EnsureInitialized()`。**

- 所以不需要任何一处代码去"记得初始化效果"：建筑实例被生成 → Unity 自己会跑 `Start`。
- 保留公开的 `Initialize(context)`：将来若真出现"由某个管理器统一注入服务"的需求，直接调它即可，
  `Start` 那次会因为已初始化而变成空操作。

**决策 31：建筑击碎矿石时，按与玩家挖矿完全相同的规则发奖励**（`grantRewardOnKill`，默认开）。

- 理由：`Ore.TakeDamage` **不自己发奖励**（阶段 1 决策 2：奖励由调用方读取 `Reward` 后发放）。
  建筑要是只管打不管发，矿石被打碎 = 玩家金币凭空消失，那不是"建筑帮玩家，是建筑在坑玩家"。
- 发奖励要走 `PlayerCurrency`（金币的唯一真相源），建筑不直接改数值。

**决策 32：计时用 `Update` 累加，不用协程 / 不用 InvokeRepeating。**

- "建筑销毁后不许留下计时器"这条，用 `Update` 是**天然满足**的：物体没了，`Update` 就没了，
  没有任何需要手动注销的注册。协程要小心 `StopCoroutine`、`InvokeRepeating` 要 `CancelInvoke`，
  而这个效果**一个都不需要**。
- 节奏：建成立刻打第一发，之后每 `attackInterval` 秒一发；`timer` 归零而不是累减，
  卡顿帧最多补打一发，不会在一帧里连打好几发。

**决策 33：用抽象基类 `BuildingEffect`，不用规格里提的 `IBuildingEffect` 接口。**

- 效果首先得是 **Unity 组件**：能挂预制体、有 Inspector 数值、能被 `GetComponentsInChildren` 找到、
  能随物体销毁自动停 —— 这些接口给不了；而"初始化 / 停用"确实需要一份共享实现。
- 规格原文也允许："如果接口对于当前 MVP 过度复杂，可以采用抽象基类。"

**决策 34：目标 = 场景里现存的矿石（`Ore` 层过滤），**没有射程**；不引入矿区组件、不引入刷新器。**

用户 2026-10-08 的原话："就用现在有的矿石系统"。结合同一天的三条规则（建筑在矿区之外 / 不按距离 /
击碎照常发奖励），落地方式是：

- **删掉 `attackRange` 字段**，删掉 `Physics.OverlapSphereNonAlloc` 查询。射程成立的前提是"建筑与目标离得近"，
  而建筑**本来就在矿区之外**，量距离没有任何意义。
- **目标查找**改为 `Object.FindObjectsByType<Ore>(FindObjectsInactive.Exclude, None)`，
  逐个过滤"存活 + 在 `oreLayers` 层里"，取离出射点**最近**的一个。
  最近优先只是让多座建筑的分工看起来合理，**不是玩法规则**。
- **不新增 `MiningZone` 之类的组件**：矿区本体与刷新逻辑用户还没做，我不替他定它的接口（原本我准备写一个，
  用户明确否掉了）。
- **代价**：每次攻击（1 秒一次）扫一遍场景里的 `Ore`，十位数量级无所谓；
  将来矿区做到成百上千个矿石时，这里换回"矿区维护的列表"即可，改的还是 `FindNearestOre()` 一个方法。
- **Gizmo 跟着改**：没有射程就没有"范围"可画，`OnDrawGizmosSelected` 改成把**当前能打到的矿石逐个连线标出**，
  不在 Ore 层上的矿石画成灰色空心块（图层配错时一眼可见）。

### 15.2 新增决策（阶段 6）

**决策 35：单场景 + 相机区域切换，不引入任何场景切换机制。**
需求一自己写了"优先对当前项目改动最小的方案"。项目里只有一个 `SampleScene.unity`，
所有系统（挖矿 / 建筑 / 商店 / UI）本来就在一个场景里跑，`Shop` 只是个空逻辑物体。
所以"三个区域"落地成**同一场景里的三个机位**，不建多场景、不做异步加载、不加场景管理框架。

**决策 36（用户拍板，S1）：商店区只做「机位 + 面板」，世界里暂时留空。**
世界里现在没有任何可看的商店实体。所以进商店区 = 相机移到商店机位 + 弹出 `ShopPanel`，
世界内不摆摊位。将来摆好了用 `AreaCameraDirector` 的右键菜单「把相机当前位置记录为商店机位」重记一次。

**决策 37（用户拍板，S2）：正开着蓝图时切区域 = 退出建造并取消蓝图，材料全部退回库存。**
走 `BuildingCameraDirector.ExitBuildMode()` → `CancelSelection()` → `CloseBlueprint(false)`
→ `OnBlueprintClosed(false)` → `ReturnAllToInventory()`（阶段 4 决策 21：**不吞玩家的料**）。
所以从建筑区点「商店」不会留下半截蓝图挂在天上。

**决策 38（用户拍板，S3）：「√」按钮改成「材料不齐就灰掉」——**推翻阶段 4 的决策 28**。**
- 需求七的「不可放置 → `√` Disabled」按**材料是否齐**解释：蓝图落位之后几何上必然可放置
  （决策 17/18：只有合法落点才能 anchor），落位之前那个 `√` 根本不显示，
  所以「不可放置」没有别的可指对象。
- 代价：`BuildingConstruction.ConfirmBuild()` 里那句「材料还不够：小砖 0/3」从此走不到。
  **那句代码保留不删**（将来别的调用方还会用到，删了会削弱它自己的自我保护）。
- 补偿：「还差几个」由面板的 `ProgressText` 一直显示着（形如「材料：小砖 2/3」），信息不丢。

**决策 39：面板按区域显隐 = `GameAreaController` 里三个 `GameObject[]` 声明式数组。**
- 只是 `SetActive` 而已，**`ShopUI` / `BuildingUI` / `ShopItemUI` / `MaterialDragItem` 一行都没改**。
- 安全性已在写代码前确认过：`ShopUI` 的订阅在 `OnEnable` / `OnDisable`（`ShopUI.cs:103/123`），
  `Awake` 只建一次条目 → 停用 / 启用是干净的；`BuildingUI` 无状态、无 `Awake`。
- **`Canvas/材料面板` 刻意不入任何数组**：它由 `BuildingManager.IsPlacing` 自己管显隐，
  而 `SlidingPanel` 就挂在这个物体上——被外部 `SetActive(false)` 会让它再也滑不回来。
  向导会在这一点上留一条警告注释。

**决策 40：建筑区的机位仍然归 `BuildingCameraDirector`，本阶段不接管。**
- 建造机位连着「蓝图跟随鼠标」「重叠检测」那一整套，阶段 3 已验证。
  再写一份只会变成两个导演抢同一个 `Transform`。
- `AreaCameraDirector` 对它是**只读属性 + 只调 public 方法**：`EnterBuildMode()` / `ExitBuildMode()` /
  `IsInBuildMode` / `IsTransitioning`，**一行都没改它**。
- 让位规则：只要 `IsInBuildMode || IsTransitioning`，`AreaCameraDirector` 完全不动相机（连速度都清零）。
- ⚠️ 已知小瑕疵：从建筑区**直接**切到商店区，`BuildingCameraDirector` 会先花
  `transitionDuration`（默认 0.6 秒）退回常规机位，`AreaCameraDirector` 让位到它退完才动身，
  所以镜头会先经过挖矿视角再拐向商店。想减轻就把那个 `transitionDuration` 调小。
  从建筑区切回**挖矿**区则完全无感——常规机位本来就等于挖矿机位。

**决策 41：挖矿闸门 = `miningInput.enabled`，外加一条 `LateUpdate` 幂等守卫。**
- 沿用决策 11 的手法（只写 `enabled`，不碰 `MiningInput` 一行）。
- `SetArea` 里设一次；另加守卫：`if (CurrentArea != 挖矿 && miningInput.enabled) miningInput.enabled = false;`
- **为什么需要守卫**：`BuildingManager` 关蓝图时会把它记下的旧值恢复成 `true`（决策 12 的
  `miningRestorePending`），而那一刻玩家可能已经站在商店区了。
- 守卫**只在非挖矿区写值**，挖矿区内一次都不写 → 不会与 `BuildingManager` 的恢复逻辑抢。

**几个值得单独记一笔的实现点：**

- **`CoinHudUI` 里真的没有 `Update` 方法**。`OnEnable` 订阅 `OnMoneyChanged` 并补刷一次当前值
  （只订阅的话，开局显示的是场景里那句占位文字）。格式串里没留 `{0}` 会走 `FormatException` 兜底，
  退化成「金币：数字」并报一次错，不会静默刷不出来。
- **`BottomNavUI` 高亮改的是 `Button.colors`（`ColorBlock`），不是 `Image.color`**：
  `Selectable` 的状态机每次状态变化都会拿 `ColorBlock` 重算 `targetGraphic` 的颜色，
  直接写 `Image.color` 会在鼠标悬停时被覆盖掉。
- **`AreaCameraDirector` 的位置与旋转时间常数一致**：位置 `Vector3.SmoothDamp(..., smoothTime, moveSpeed)`，
  旋转用同一条时间常数的指数平滑 `Slerp(rot, target, 1 - exp(-dt / smoothTime))`，
  所以调 `SmoothTime` 时两者的"软硬"是一起变的。
- **`BuildingSpawnPop` 的所有写入都被 `Application.isPlaying` 拦住**：

三个机位（`AreaCameraDirector` 上的字段，全部 Inspector 可调）：

| 区域 | 字段 | 默认值 | 谁在管 |
|---|---|---|---|
| 挖矿 | `miningPosition` / `miningEulerAngles` | `(-20.93, 0.82, -12.9)` / `(0,0,0)` | `AreaCameraDirector` |
| 商店 | `shopPosition` / `shopEulerAngles` | `(-23.49, 22, -23.28)` / `(45,0,0)` | `AreaCameraDirector` |

  按下「挖矿」→ 相机走完约 20 米的距离大约 1 秒出头；想在 Inspector 上调。
- `snapOnStart = true`：进 Play Mode 时相机**直接落在起始区域**的机位，不播过渡。

7. **落位**：把蓝图移到合法落点后**点一下地面**（不是点 `√`）→ 进入 Filling 阶段。
   - **几何不允许的点** → 蓝图是**红色**；合法落点 → **绿色**（需求十二，阶段 3 原有）。
   - 落位**之前**拖材料会被拒绝并提示「请先把蓝图放到地面上」
     （`CanAcceptMaterial` 要求 `Phase == Filling`，`BuildingConstruction.cs:194`）。
   - 面板在落位前后是同一个，不会重新滑一次。
8. **拖材料**：把「红色小砖」从面板拖到蓝图上 → 进度变「小砖 1/3」，`√` 仍然灰。

   - 第一次：**撤掉刚放的那块料**，进度回「小砖 0/3」，库存加回来（需求九的"有材料 → 撤料"）。
   - 第二次：**撤掉蓝图**，材料面板滑回去（需求九的"没材料 → 撤蓝图"）。
   - 再点一次 [风琴博物馆]，重新落位，把 3 块红砖全放进去 → **`√` 变成可点**（决策 38）。
10. **点 [√]**：建筑被生成，**从 0.8 弹到 1**（`BuildingSpawnPop`，需求十二），材料面板滑回去。
11. **自动攻击**：刚建好的风琴博物馆每秒打一次最近的矿石（**不按距离**，见决策 34 / 阶段 5）。
    Scene 视图里能看到 `Debug.DrawLine` 的攻击线（Game 视图要看 Gizmos）。
12. **货币继续涨**：建筑打碎矿石也会加钱，右上角的数字跟着跳（需求十四的闭环）。
13. **切区域取消蓝图**：重新点 [风琴博物馆] 让蓝图出现 → 点底部 [商店] 或 [挖矿]
    → 蓝图消失、**已放进去的材料全部退回库存**（决策 37，不吞料）→ 再进建筑区重新建。
14. **建筑 → 挖矿**：点 [挖矿]，相机从建造视角平滑退回原机位（无感，因为常规机位 = 挖矿机位）。

### 15.14 阶段 6 首次实机跑出来的缺陷：建筑面板里没有按钮（2026-10-08）

**排查链路**（逐环 grep `SampleScene.unity` 核实，没有一环靠推理）：

| # | 环节 | 结果 |
|---|---|---|
| 1 | 点 [建筑] → 有日志 `[GameAreaController] 区域切换：挖矿 → 建筑` | ✅ |
| 2 | `buildingAreaPanels` 的内容 | ✅ `Size 1` → `BuildingPanel` |

阶段 3 的**从来没补** —— 本文档原先在 §13.3 里写「阶段 3 / 4 的向导已修」，那句是错的，已更正。
**只要重跑一次阶段 3 向导，就会重新造出三个关闭的按钮**，而且从 Console 看不出跑过几次。

**修法**（三处，两处治病、一处堵规则 5 的静默缺口）：

| 文件 | 位置 | 改动 | 作用 |
|---|---|---|---|
| `Scripts/Editor/BuildingSetupWizard.cs` | `CreateButton()`，`clone.name = …` 之后 | 补 `clone.SetActive(true);` + 注释 | **治本**：不补，重跑一次就又坏一次 |

`BuildingGrid` 的关键约定：

```text
origin = gridCenter - (cellCounts * cellSize) / 2
WorldToCell(p) = (floor((p.x - origin.x) / cellSize), floor((p.z - origin.z) / cellSize))

// n = FootprintCells(footprint)
cellLineX = (n.x 为奇数) ? floor(u) + 0.5 : floor(u + 0.5)   // 偶数格取最近交点
cellLineZ = (n.y 为奇数) ? floor(v) + 0.5 : floor(v + 0.5)
rect = (ceil(cellLineX - n.x/2 - 1e-4), ceil(cellLineZ - n.y/2 - 1e-4), n.x, n.y)
snappedCenter = origin + (cellLineX, 0, cellLineZ) * cellSize
```

占用表用 `bool[]`，ownerId = 建筑实例的 `GetInstanceID()`；`Dictionary<int, RectInt>` 保存
ownerId → 占地矩形，供拆除时精确释放。

### 16.9 阶段 7 实测发现的挖矿回归（已修，待复验）

**现象**：在建筑区选中蓝图后，不点「取消蓝图」，直接点底部「挖矿」回到挖矿区；
之后点击矿石完全没反应，Console 连 `[MiningInput] 点击落空` 都没有 ——
说明 `MiningInput` 组件根本没在监听输入。

**根因**（时序，全部由 Editor.log 实证）：

1. 切到建筑区时，`GameAreaController.ApplyMiningGate` 把 `MiningInput.enabled` 设为 `false`；
2. 选中蓝图时 `BuildingManager.SetMiningSuppressed(true)` 记下
   `miningEnabledBeforeSuppression = false`（它记的是“区域门关掉之后”的值），再把组件关一次；
3. 点「挖矿」切回：`ApplyMiningGate(Mining)` 先把组件打开；
4. 紧接着 `AreaCameraDirector` 退出建造视角 → `CancelSelection` →
   `SetMiningSuppressed(false)` 原实现无条件把 `miningRestorePending = true`；
5. `BuildingManager.LateUpdate` 把组件“恢复”成第 2 步记下的 `false`。

结果：刚被区域门打开的 MiningInput 又被关掉，而且 `GameAreaController.LateUpdate`
只在**非挖矿区**强制关闭，不会在挖矿区强制打开，所以它一直保持关闭。

**修法**：`SetMiningSuppressed(false)` 改成
`miningRestorePending = miningEnabledBeforeSuppression;`
—— 屏蔽前本来就是关的，说明这次关闭不是本类造成的，释放时也不要替别的系统写值。
区域门在切回挖矿时会把组件打开，之后不会再被 `BuildingManager` 覆盖回 `false`。

**复验**：建筑区开蓝图 → 直接点「挖矿」→ 点矿石应正常掉血；
Console 应重新出现 `[Ore] ... 受到 X 点伤害`。离线编译 0 error / 0 warning。

### 18.3 修复：建筑必须隔一格才能放置

建筑碰撞体是 4×4，紧贴时两个盒子面贴面；PhysX 的 contact offset 会让接触也命中查询。

**修法**：`BuildingPlacement.cs` 改用 `Physics.OverlapBoxNonAlloc`，跳过已登记在
`BuildingManager.PlacedBuildings` 里的建筑碰撞体；Physics 只兜底「Building 层但没经过网格登记」的碰撞体。
已登记建筑之间的占用仍由 `BuildingGrid.CanPlace` 精确到格判定。

### 21.2 运行机制（下次改代码前先看这里）

- 存档版本 **2**。`checksum` 覆盖除 `checksum` 本身外的全部 JSON：
  先清空并序列化一次求 FNV-1a，再填回并序列化最终文本。
- 读取顺序：`save.json` → `.bak` → `.bak2`。每一代都要完整解析 + 结构校验；

- `OnApplicationQuit` / 失焦 / 定时自动保存都会跳过 `loadFailed`；

- 建筑：建造与恢复都会挂 `PlacedBuildingInfo`（`BuildingData`、占地 `RectInt`、楼层颜色）。
  读档先 `ClearPlacedBuildings()`，再按存档逐座 `RestoreBuilding()`；
  恢复使用新的 `InstanceID` 重新登记占地，最后重算等级。

- 建造 / 拆除触发的自动保存只置标记，统一在 **LateUpdate** 执行，
  避免在 `ConfirmBuild` 回调中间写出「蓝图还没结算完」的半成品状态。
- 读档期间 `isLoading = true`：`ClearPlacedBuildings()` 触发的 `OnBuildingRemoved` 不会产生自动保存。
- 定时保存使用 `unscaledTime`，默认 60 秒；代码把间隔下限钳到 1 秒，防止 Inspector 误填 0 后每帧写盘。

  不再先退回常规机位再拐弯。

### 22.2 运行机制（改代码前先看这里）

- `EventBus` 是静态类型化总线：`Subscribe<T>` 在 `OnEnable`，`Unsubscribe<T>` 在 `OnDisable`；
  事件全部是 `readonly struct`（`Core/Events/GameEvents.cs`）。静态字典在
  `SubsystemRegistration` 时清空，关闭 Domain Reload 也不会把上一局订阅者带进来。
- 单个订阅者抛异常会被 `EventBus` 捕获并打红字，其他订阅者继续执行。
- **发布纪律：先提交状态，再发布事件**。例如 `BuildingPlaced` 在 `selectedBuilding = null`、
  蓝图销毁之后才发；订阅者读到的 `BuildingManager` 已经是完成态。
- **读档不发声**：
  - `PlayerCurrency.RestoreMoney()` 与 `MaterialInventory.RestoreStacks()` 只发旧事件，不发 EventBus；
  - `BuildingConstruction.DiscardCurrentBlueprintWithoutRefund()` 走 `CancelSelection(false)`；
  - `BuildingManager.ClearPlacedBuildings()` 用 `suppressRemovedEventDepth` 压掉 `BuildingRemoved`。
- 事件发布点：金币、库存、等级、区域、蓝图打开 / 落位 / 关闭、建造 / 拆除、材料放入 / 撤回、
  建造进度、提示行、购买成功 / 失败、矿石受击 / 击碎、存档 / 读档完成。
- `AudioManager` 订阅 EventBus 自动配音；`AudioCatalog` 里没有对应条目时是**空操作**，不报错。
  同一个 ID 有 `cooldownSeconds`（默认 0.05），防止一次点击触发多个事件叠成爆音。
- `AudioManager` 的音量键：`yujian.audio.master` / `music` / `sfx` / `ui`，范围 0~1，音乐音量即时生效。
- `UIManager` 场景里没挂也能用：第一次 `Open` 时自动创建 `[UIManager]` 物体并扫描全场景 `UIPanel`
  （含未激活物体）。`UIPanel` 不改变面板初始状态，只有被 `Open/Close` 调用时才动。
- `UIPanel` 显隐优先级：`SlidingPanel` → `CanvasGroup`（自动补）→ `SetActive`；
  最后一种在 target 就是自己时会拒绝并改用 CanvasGroup，避免把组件一起停掉。
- `PointerOverUI.IsOver(screenPosition, context, ref warned)` 保留每个调用方各自的一次性警告标记，
  三处行为现在完全一致。

## 二十四、2026-10-23 观察模式系统（代码完成，待 Unity 向导与实机验证）

### 24.1 规则

- **开局仍在挖矿**（`GameAreaController.startArea = Mining`）。观察模式不是开局状态。
- 玩家处于任一系统（挖矿 / 建筑 / 商店）时，**再次点击当前系统的底部导航按钮** →
  退出该系统，进入观察模式。
- 建筑面板的「退出建造」→ 同样进入观察模式，并按既有规则取消未放置蓝图、退回材料。
- 观察模式下点击任意系统按钮 → 进入该系统。
- 观察模式没有底部导航按钮，也不高亮任何按钮；没有区域面板，挖矿输入关闭。
- 状态模型：`GameArea.Observation = 3`，不另起一套并行状态。
  区域仍然只决定三件事：**相机去哪、哪些面板显示、能不能挖矿**。

### 24.2 相机

**操作（2026-10-23 用户确认）**

| 输入 | 行为 |
|---|---|
| 滚轮 | 缩放：改变焦点到相机的距离（默认 40–200，每格 8） |
| 按住鼠标中键拖动 | 绕焦点旋转（默认 0.25°/像素，俯仰限制 15°–85°） |
| 按住鼠标右键拖动 | 在地面平面上平移焦点（默认灵敏度 1，相对观察机位最多 ±80） |

- 指针在 UI 上时不响应旋转 / 平移 / 缩放；一次拖动从 UI 开始时整段不响应。
- 中键与右键同时按住时优先旋转，避免同一帧位移被两边重复消费。

**相机归属**

- `AreaCameraDirector` 负责把相机送到观察机位：
  - 从挖矿 / 商店过来：走现有 SmoothDamp；
  - 从建筑过来：调用 `BuildingCameraDirector.ExitBuildMode(观察机位, 观察旋转)`，
    一次过渡到位，同时取消未放置蓝图。
- 到位后调用 `ObservationCameraController.BeginControl()`；控制器从相机最终姿态反推
  焦点、距离、偏航、俯仰，然后开始响应输入。观察机位只在 `AreaCameraDirector` 里配一份。
- 建造导演还在建造 / 过渡时，观察控制器完全让位，不写相机。

**默认观察机位**

- 焦点：海岛中心 `(10.21735, 0, -9.49205)`
- 俯仰 55°，偏航 0°，距离约 130
- 相机位置 `(10.21735, 106.49, -84.06)`
- 想换成自己摆的镜头：选中 GameAreaSystem 上的 `AreaCameraDirector`，
  在 Scene 视图摆好后右键组件 →「把相机当前位置记录为观察机位」。

### 29.3 验证

- 离线编译 `Assembly-CSharp` 与 `Assembly-CSharp-Editor` 均 **exit 0**。
- **未验证**：Unity 内实际亮度、矿灯是否过曝 / 过暗、软阴影性能、相机背景切换是否突兀。

### 29.4 实机步骤

1. 切回 Unity，等编译完成，Console 无红字。
2. 运行菜单 **屿见 → 挖矿 → 配置矿洞照明（阶段 12）**。
   - 场景里应出现「矿洞灯光」：矿石右侧一盏灯柱 + 发光方块，外加三盏点光；
   - 同一物体下还有一个 `Cave` 子物体，包含后墙、左右墙、顶板和几块碎石。
3. 进 Play Mode，从矿山进入挖矿区：
   - 画面应逐渐变暗、背景变黑，矿石被暖色光照亮，灯泡轻微闪烁；
   - 太阳光变暗，但没有完全消失；
   - 点底部「挖矿」回观察模式，岛上恢复白天。
4. 觉得太暗 / 太亮时，选中「矿洞灯光」，调 `Mining Sun Intensity`、`Mining Ambient`、`Mining Background`；
   单盏矿灯的亮度在 `Key Light` / `Fill Light` / `Rim Light` 的 Intensity 上调。

### 29.5 已知限制

- 矿洞墙体是基础几何体拼的占位盒子，等待美术替换；替换时保持 `矿洞灯光/Cave` 这个层级即可继续沿用显隐逻辑。
- 墙体没有碰撞体，只负责视觉；玩家不需要在矿洞里走动，所以不影响操作。
- 相机背景是瞬时切换，亮度是 0.6 秒渐变；进出时可能看到一次背景跳变。
- 点光阴影只开在主光上，移动端性能仍建议实测；卡的话把 `Key Light` 的 Shadows 改成 None。
- 需要运行一次向导才会写入场景，尚未提交。
